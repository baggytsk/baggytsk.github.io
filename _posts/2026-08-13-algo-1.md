### 0. 먼저 알아둘 기초 이론

#### 그리디 (Greedy, 탐욕법)

- 매 순간 **"지금 당장 제일 좋아 보이는" 선택**만 하는 방법
- 장점: 빠르고 단순하다
- 단점: **눈앞의 최선이 전체의 최선을 보장하지 못한다.**


#### 동적 계획법 (DP, Dynamic Programming)
 
- 큰 문제를 **작은 부분 문제로 쪼갠 뒤**, 부분 문제의 답을 **저장해서 재사용**하는 방법
- 두 가지 조건이 맞아야 DP가 통한다.
  1. **최적 부분 구조**: 큰 문제의 최적해가 부분 문제들의 최적해로 조립된다
  2. **겹치는 부분 문제**: 같은 부분 문제가 반복 등장한다(그래서 저장이 이득)
- 꼭 알아야 할 용어 세 가지:
  - **상태(state)**: 부분 문제를 구분하는 정보
  - **점화식(recurrence)**: 상태들 사이의 관계식 (자식들의 답으로 부모의 답을 만든다)
  - **메모이제이션(memoization)**: 한 번 구한 답을 배열에 저장해 두고 다시 계산하지 않는 것


#### 트리 DP (Tree DP)
 
- 데이터가 **트리(부모-자식 구조)** 로 주어질 때 하는 DP
- 보통 **DFS로 잎(리프)부터 뿌리(루트)까지** 부분 답을 합쳐 올라간다. 이렇게 "자식을 먼저 다 계산하고 부모를 계산"하는 순서를 **후위순회(post-order)** 라고 한다
- 각 노드에 몇 개의 **상태**를 두고, 자식들의 상태로 부모의 상태를 채운다


#### 정점 커버 (Vertex Cover)
 
- 그래프에서 **모든 간선(edge)이, 선택된 정점(vertex)을 최소 한쪽 끝점으로 갖도록** 정점을 고르는 것
- **최소 정점 커버**: 그렇게 고른 정점의 수(또는 가중치 합)를 **최소**로 만드는 것

#### 시간 복잡도 표기 O(N)
 
- 입력 크기 `N`에 **비례**해서 연산량이 늘어난다는 뜻. 트리의 모든 노드를 한 번씩만 방문하면 `O(N)`이다.

### 1. 문제 요약
 
회사 조직은 **트리 구조**이며, 각 직원에 `하루평균 매출액(sales)`이 주어지고 `links[i] = [팀장, 팀원]`으로 상하 관계가 주어진다.
 
워크숍 참석자를 고르는데:
 
- **모든 팀은 최소 1명 이상** 참석해야 한다.
- 참석자들의 매출액 합이 **최소**가 되도록 한다.

여기서 **한 팀 = 팀장 한 명 + 그 팀장의 직속 팀원들**이며, 트리에서 자식이 있는 노드(팀장)마다 하나의 팀이 생긴다.

<br>

<br>

### 2. 설계

> 그리디가 안 되는 이유 : 한 직원의 참석 또는 불참 결정이 위·아래로 **연쇄적으로** 영향을 줘서, 국소적 최선이 전역 최선을 보장하지 못한다. 
-> 그래서 DP가 필요함

> 정점 커버가 아닌 이유 : **간선**마다 최소 한쪽 끝점 참석이 아니라 팀간 한 명 참석이라 요구하는 조건과 다르다.

<br>

따라서 트리 DP로 설계한다.
각 노드에 **참석 / 불참** 두 상태를 둔다.
 
- `dp[u][0]` = **u가 불참**할 때, u의 서브트리에서 모든 팀 제약을 만족하는 최소 비용
- `dp[u][1]` = **u가 참석**할 때, 최소 비용
DFS 후위순회(자식 먼저 계산)로 아래에서 위로 채운다.

### 3. 전체 코드 (Java)
 
```java
import java.util.*;
 
class Solution {
    long[][] dp;
 
    public int solution(int[] sales, int[][] links) {
        Map<Integer, List<Integer>> graph = new HashMap<>();
        for (int[] link : links) {
            graph.computeIfAbsent(link[0], k -> new ArrayList<>()).add(link[1]);
        }
 
        dp = new long[sales.length + 1][2];
        dfs(1, graph, sales);
 
        return (int) Math.min(dp[1][0], dp[1][1]);
    }
 
    void dfs(int node, Map<Integer, List<Integer>> g, int[] sales) {
        List<Integer> children = g.getOrDefault(node, Collections.emptyList());
 
        if (children.isEmpty()) {         // 리프 노드 = 팀장이 아님 → 팀 제약 없음
            dp[node][1] = sales[node - 1];
            dp[node][0] = 0;
            return;
        }
 
        long base = 0;
        boolean hasAttend = false;           // 싼 선택 중 이미 참석한 자식이 있나
        long extra = Long.MAX_VALUE;         // 자식 하나를 참석으로 바꾸는 최소 추가비용
 
        for (int child : children) {
            dfs(child, g, sales);
            base += Math.min(dp[child][0], dp[child][1]);
            if (dp[child][1] <= dp[child][0]) hasAttend = true;
            extra = Math.min(extra, dp[child][1] - dp[child][0]);
        }
 
        dp[node][1] = sales[node - 1] + base;          // node 참석 → 팀 OK, 자식 자유
        dp[node][0] = hasAttend ? base : base + extra; // node 불참 → 자식 최소 1명 참석
    }
}
```

### 4. 주의할 구현 포인트
 
- **오버플로우 → `long`**: `sales.length ≤ 300,000`, `sales[i] ≤ 10,000`이라 부분합이 최대 약 `3 × 10⁹`로 `int`(약 21억)를 넘는다. `dp`는 반드시 `long`으로 두고 최종 답만 `(int)` 캐스팅한다. (최종 정답 자체는 `2³¹-1` 이하 보장.)
- **인덱싱**: 노드는 1-인덱스, `sales`는 0-인덱스 → `sales[node - 1]`.
- **재귀 깊이**: 트리가 한 줄로 길게 늘어지면(최악 30만 depth) 재귀 DFS가 `StackOverflowError`를 낼 수 있다. 이때는 명시적 스택으로 반복 DFS(post-order)로 바꾸거나, 큰 스택 크기의 별도 `Thread`에서 실행한다.

- 각 노드/간선을 한 번씩만 방문 → **시간 O(N)**, **공간 O(N)**.

## 6. 한 줄 회고
 
- 이 문제는 단순한 "간선 커버"가 아니라 "**팀(노드+자식) 커버**"임을 알아채야했습니다.
- **불참 시 자식 최소 한 명 강제**의 규칙을 족용하여 gap 최솟값으로 `O(N)`에 처리하는 것과  **`long` 오버플로우 방어**를 체크해야했습니다.
